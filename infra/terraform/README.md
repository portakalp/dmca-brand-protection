# Google Cloud reference deployment (optional)

This directory is an **optional reference deployment** of Kalkan on Google Cloud: Cloud Run for the API and the panel, one Compute Engine VM for the workers, and a Cloudflare Worker at the edge. You do not need it to try or run Kalkan:

- to try the demo on a laptop, use `make demo` (see the repository README);
- to run Kalkan on your own Linux server with Docker Compose, use [`deploy/selfhost`](../../deploy/selfhost/).

It is kept because it shows how the same code runs on managed infrastructure with least-privilege service accounts, no long-lived keys, and generated secrets that never reach the Terraform state. Everything here runs on, and costs money on, your own Google Cloud and Cloudflare accounts.

## Shape

```
              Cloudflare edge Worker (infra/cloudflare)
              app.<domain>          evidence.<domain>
                   │  X-Edge-Auth        │
         ┌─────────┴────────┐            │
   Cloud Run web      Cloud Run api ◄────┘
   (Next.js panel)    (FastAPI) ─────────────┐
                           │                 │
                     Cloud SQL (Postgres 16) GCS buckets (evidence, reports)
                           │                 │
   Compute Engine VM kalkan-vm (infra/compose/docker-compose.vm.yml):
   cloud-sql-proxy, redis, worker-default, scheduler, ct-consumer, certstream,
   worker-browser, worker-ai, ops, Prometheus, Alertmanager, Grafana
```

- One Terraform root, no modules; resources are split by service: `apis.tf`, `network.tf`, `iam.tf`, `wif.tf`, `artifact_registry.tf`, `sql.tf`, `secrets.tf`, `storage.tf`, `compute.tf`, `cloud_run.tf`, `monitoring.tf` (architecture.md §22).
- The VM has no public inbound port: SSH only through IAP TCP forwarding with OS Login. The ops panel, Grafana and Prometheus listen on 127.0.0.1 and are reached through an IAP SSH tunnel.
- `infra/vm/startup.sh` installs Docker and the gcloud CLI at boot; `infra/compose/vm/` holds the VM's configuration, systemd units and scripts (`deploy.sh`, `load-secrets.sh`, `firewall.sh`, `db-bootstrap.sh`, `render-alertmanager.sh`).

## Setting it up

You run every command yourself, with your own credentials.

1. `PROJECT_ID=my-gcp-project ./bootstrap.sh` enables the APIs and creates the versioned state bucket `<project_id>-tfstate`.
2. `cp terraform.tfvars.example terraform.tfvars` and fill it in. Required: `project_id`, `domain`, `ops_alert_email`, `github_repo`, `github_repository_id`, `github_deployer_id`. The GitHub ids come from `gh api repos/portakalp/dmca-brand-protection --jq .id` and `gh api users/LOGIN --jq .id`; Workload Identity Federation compares numeric ids because names can be re-registered.
3. `terraform init -backend-config="bucket=<project_id>-tfstate"`, `terraform plan -out=tfplan`, read the plan, `terraform apply tfplan`.
4. Add versions to the secrets Terraform does not generate (`printf '%s' "$value" | gcloud secrets versions add <id> --data-file=-`):
   - required: `edge-shared-secret` (for example `openssl rand -hex 32`) and `totp-encryption-key` (a Fernet key: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`);
   - optional, each one turns a feature on: `postmark-server-token` and `postmark-webhook-basic-auth` (abuse notices and reply tracking through Postmark), `alert-smtp-password` (Alertmanager e-mail through any SMTP relay), `anthropic-api-key`, `proxy-map`, `webrisk-api-key`, `czds-username` and `czds-password`, `sentry-dsn`, `grafana-admin-password`.
5. `terraform output -raw github_variables` prints ready `gh variable set` commands for a deploy workflow.
6. Deploy the edge Worker from [`infra/cloudflare`](../cloudflare/README.md).

Database passwords, `DATABASE_URL_*`, the VM Redis ACL passwords and the `REDIS_URL`s are generated by Terraform and written to Secret Manager through write-only arguments, so they never reach the plan or the state (K78). Rotate them by bumping `db_password_version` or `redis_password_version`, applying, and deploying again.

## Deploying

The repository ships no deploy workflow, because a deploy needs your cloud account. `wif.tf` trusts exactly one workflow file (`github_deploy_workflow`, default `.github/workflows/deploy.yml`) in `github_repo`, and only a first-attempt `workflow_dispatch` run on `main` started by `github_deployer_id`. A deploy, from such a workflow or by hand, runs these steps in order:

1. **Check the api secrets.** `database-url-api` and `edge-shared-secret` must have an enabled newest version. The optional ones (`totp-encryption-key`, `postmark-server-token`, `postmark-webhook-basic-auth`, `sentry-dsn`) are bound to Cloud Run only when their newest version is enabled, because Cloud Run fails a revision whose secret has no usable version.
2. **Build and push** `infra/docker/{backend,browser,web}.Dockerfile` to `terraform output artifact_registry`, tagged with the git SHA.
3. **Bundle the VM files:** `infra/compose/docker-compose.vm.yml` as `docker-compose.yml`, `infra/compose/vm/` as `vm/`, `backend/sql/bootstrap_roles.sql` as `sql/bootstrap_roles.sql`, a compose `.env` (`REGISTRY`, `IMAGE_TAG`, `CLOUDSQL_INSTANCE`, `GCP_PROJECT_ID`, `COMPOSE_PROFILES`, `APP_BASE_URL`) and an `app.env`: `infra/compose/vm/app.env` plus this deployment's `GCS_EVIDENCE_BUCKET`, `GCS_REPORTS_BUCKET`, `APP_BASE_URL`, `EVIDENCE_BASE_URL`, `MAIL_FROM`, `REPLY_DOMAIN`, `DRY_RUN_REDIRECT_EMAIL`, `CASE_PREFIX`, `OPS_ALERT_EMAIL`, `ALERT_SMTP_SMARTHOST` and `ALERT_SMTP_USERNAME`. Refuse the bundle if `SSRF_ALLOW_CIDRS` or `STORAGE_EMULATOR_HOST` appears in it, or if a service does not run with `ENV=prod`.
4. **Deploy the VM:** copy the bundle with `gcloud compute scp --tunnel-through-iap`, unpack it as root into a root-only directory and run `sudo bash vm/bin/deploy.sh <image_tag>`. It installs the systemd units and the firewall, loads the secrets, runs `db-bootstrap.sh` and the migrations, then `docker compose up`. Migrations run here, before Cloud Run gets the new image.
5. **Deploy Cloud Run:** `gcloud run deploy api --image <registry>/backend:<tag> --port 8000 --service-account kalkan-api@<project>.iam.gserviceaccount.com --set-cloudsql-instances <connection name> --env-vars-file <file> --set-secrets <bindings from step 1>`, with `ENV=prod`, `EMAIL_PROVIDER`, `LOG_LEVEL`, `NOTICES_DRY_RUN` and the shared settings from step 3 in the env file. Then `gcloud run deploy web --image <registry>/web:<tag> --port 3000 --service-account kalkan-web@<project>.iam.gserviceaccount.com --set-env-vars APP_BASE_URL=https://app.<domain> --set-secrets EDGE_SHARED_SECRET=edge-shared-secret:latest`. Terraform created both services and keeps their scaling; the deploy owns image, port, resources, env and secrets (K79).
6. **Health checks:** `GET <api_url>/api/health` on run.app, `https://app.<domain>/api/healthz` through the edge, and a request to an unknown API path through the edge: 404 means the api accepted the Worker's secret, 403 means the two secrets differ.

A rollback is the same deploy with an earlier image tag and `deploy.sh <tag> --skip-migrations`; schema downgrades are manual.

## Notes

- The Cloud Run `api` and `web` services start with a placeholder image; the container fields in `cloud_run.tf` only apply when a service is created.
- The api's own Cloud Run request logs drop `/e/<token>` evidence links (log exclusion `kalkan-api-evidence-links`; K35), and the edge Worker's invocation logs are off.
- The evidence bucket's retention policy is unlocked. Locking is irreversible, so this reference never sets `is_locked = true`.
- Alertmanager on the VM sends through any SMTP relay: `ALERT_SMTP_SMARTHOST` and `ALERT_SMTP_USERNAME` in `app.env` and the `alert-smtp-password` secret, rendered by `infra/compose/vm/bin/render-alertmanager.sh`. Without them alerts are dropped and the reason is logged.
- Local checks without cloud credentials: `make infra-check` runs Terraform fmt and validate, tflint, the VM compose file, promtool and shellcheck in pinned Docker images. The provider lock file (`.terraform.lock.hcl`) is committed; after a provider upgrade, refresh it with `terraform providers lock -platform=linux_amd64 -platform=linux_arm64 -platform=darwin_arm64 -platform=darwin_amd64`.
